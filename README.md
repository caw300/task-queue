# Distributed Task Queue

A task queue with a coordinator ("broker") and any number of independent
worker processes that pull work from it. Built to actually demonstrate the
core ideas behind systems like Celery, Sidekiq, or AWS SQS + Lambda — not
just simulate them.

## What it demonstrates

- **Atomic task claiming.** Multiple workers poll the same broker at once.
  The broker uses a single SQL `UPDATE ... WHERE id = (SELECT ...) RETURNING`
  inside an immediate transaction, so two workers can never be handed the
  same task, even under concurrent load. This is the same core pattern
  real message-queue systems use for "exactly-once delivery to a consumer."
- **Fault tolerance via leases.** When a worker claims a task, it gets a
  time-limited lease. If the worker crashes mid-task, it never reports back,
  and the broker's background "reaper" notices the lease expired and puts
  the task back in the queue — automatically, without any special crash
  handling in the worker.
- **Retries with exponential backoff.** Failed tasks are retried up to
  `max_retries` times, with the delay between attempts growing each time
  (2s, 4s, 8s...), which is how you avoid hammering a dependency that's
  already struggling.
- **Priority scheduling.** Higher-priority tasks are claimed first.
- **Delayed / scheduled execution.** Tasks can be submitted with a
  `run_at` in the future (e.g. "send this reminder in 24 hours").
- **Horizontal scaling.** Workers are just processes that speak HTTP to the
  broker — run 1 or 50 of them, on one machine or many, with no code changes.

## Architecture

```
                 ┌─────────────┐
   submit task → │             │
                 │   broker    │ ← SQLite (source of truth, WAL mode)
   claim task  ← │  (FastAPI)  │
   report result │             │
                 └─────────────┘
                    ▲   ▲   ▲
                    │   │   │  HTTP polling
              ┌─────┘   │   └─────┐
          worker-1   worker-2   worker-3   ← run as many as you want,
                                              anywhere with network access
```

## Setup

```bash
pip install -r requirements.txt
```

## Running it

**Terminal 1 — start the broker:**
```bash
python broker.py
```
Dashboard: http://localhost:8000/dashboard
API docs (auto-generated by FastAPI): http://localhost:8000/docs

**Terminal 2, 3, 4... — start one or more workers:**
```bash
python worker.py --id worker-1
python worker.py --id worker-2   # run more for real parallelism
```

**Terminal 5 — run the demo, or submit tasks yourself:**
```bash
python demo.py
```
Watch the dashboard update live as tasks move from `pending` → `running` →
`completed`/`failed`, including retries on the flaky demo task.

## Using it in your own code

```python
from client import TaskQueueClient

q = TaskQueueClient("http://localhost:8000")
task_id = q.submit("add", args=[2, 3], priority=5)
result = q.wait(task_id)
print(result["result"])  # 5
```

Add your own task types by writing a function in `tasks_example.py` (or your
own module) and adding it to `REGISTRY` — any worker that imports it can
then execute tasks of that name.

## Where to take this further

- **Swap SQLite for Postgres/Redis** to run the broker itself across
  multiple machines instead of one.
- **Long-polling instead of fixed-interval polling** on `/tasks/claim` to
  cut latency and request volume.
- **Task dependencies / DAGs** — let a task specify "don't run until tasks
  X and Y complete," turning this into a mini Airflow.
- **Authentication** on the broker API if it's exposed beyond localhost.
- **Dead-letter queue** — a place permanently-failed tasks land for
  inspection, instead of just sitting as `status='failed'`.
- **Structured logging / metrics** (e.g. task duration histograms) exported
  to Prometheus.
